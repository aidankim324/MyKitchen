# MyKitchen

Personal kitchen inventory (fridge / freezer / pantry) built with Next.js 16 App Router, React 19,
TypeScript, Tailwind CSS 4, Clerk, Prisma 7 (`@prisma/adapter-pg`) on Supabase Postgres, Zod, and
Vitest. Deployed on Vercel. It is also a portfolio project, so code should read as deliberate and
maintainable, not generated.

**The repository is the source of truth.** If this file, `docs/ARCHITECTURE.md`, or any handoff note
disagrees with the code or git history, trust the code and flag the discrepancy.

## Before changing anything

- Check `git status`, the current branch, and recent `git log`. Don't assume a described change
  exists, was committed, was pushed, or was deployed.
- Read the files you're about to change and the helpers they use. Reuse what exists before
  creating anything new.
- Make the narrowest change that solves the task. No drive-by refactors, renames, or reformatting.

## Commands

- `npm run check`: lint, tests, and production build. Run it before every meaningful commit.
- `npm test` / `npm run lint`: for quicker iteration.
- `git diff --check`: check for whitespace errors before committing.
- Stage files explicitly. Never `git add .`, because local diagnostic or database scripts may exist.
- Never `npm audit fix --force`. Evaluate dependency changes one at a time.

## Security invariants (never weaken these)

- Every private inventory read or mutation is scoped by **both** item `id` and the Clerk `userId`.
  The owner condition belongs **in the query or mutation itself**, not in a separate pre-check.
- Server-side Zod validation (`validations/item.ts`) is authoritative. Client validation exists only
  for UX. Never trust client-supplied IDs, enum values, or computed state.
- Never print, log, commit, or paste secrets (Clerk keys, `DATABASE_URL`, Vercel env). Use
  `.env.local` or the configured environment. `.env.example` holds placeholders only.

## Guest mode

- `/guest` and `/guest/inventory` are public, read-only, and fixture-backed (`lib/guest-inventory.ts`).
- Guest mode never touches the database, a shared Clerk account, or the item APIs (no POST, PATCH,
  or DELETE). Don't merge guest and authenticated components if doing so blurs that boundary.

## Data model and domain rules

- Prisma schema: `prisma/schema.prisma`. Change it only through migrations in `prisma/migrations/`.
  Never alter the live database by hand, because the schema would drift from the migrations.
- `id` uses `@default(uuid())`, which Prisma generates on the **client**. There is no database
  default. Any raw SQL insert must supply an ID explicitly. Prefer the Prisma client for scripts.
- Enum lists (locations, categories, units) live in `validations/item.ts` and the Prisma schema.
  Import them; don't copy them.
- Storage display order is always Fridge, Freezer, Pantry.

## Dates

- Food dates are **calendar dates** (`YYYY-MM-DD`), stored as Postgres `DATE`.
- "Today" means the user's calendar date, not the UTC date.
- Expiration status: `expired` (before today), `expiring_soon` (today through +7 days), `fresh`
  (more than 7 days), `no_date` (null).
- Use the helpers in `lib/dates.ts`. Never parse with `new Date("YYYY-MM-DD")` or roll ad-hoc date
  math inside components.

## Database scripts and data safety

- Any script that deletes or rewrites data must: preview, uniquely identify the target owner,
  require explicit confirmation, run in a transaction, and verify counts afterward. Never write an
  unscoped `DELETE FROM kitchen_items`.
- Multiple users have data. Never infer the target user just because rows exist.
- Personal seed or diagnostic scripts stay out of git unless rewritten as generic, safe tooling.

## UI and design

- Restrained, premium utility look: warm off-white background, charcoal text, sage accent, thin
  borders, subtle shadows, radii of roughly 10–14px, compact controls, and dense inventory cards.
  Use the tokens in `app/globals.css`.
- Avoid gradients, glassmorphism, giant KPI cards, heavy shadows, saturated colors, and decoration
  for its own sake. Don't add copy or badges just to fill space.
- The app layout width is `max-w-[110rem]`. Changes must work at every width, not just 1440×900
  and 390×844. No screenshot-specific hacks.
- Keep controls accessible and respect `prefers-reduced-motion`, especially for the landing-page
  fridge animations.
- Item artwork is lightweight transparent SVG in `public/item-images/`, generated by
  `scripts/create-item-images.mjs`. Keep the generator so the assets stay reproducible.
- No Three.js or React Three Fiber unless explicitly requested. If it's ever added, it belongs only
  on the landing page.

## Code style

- Small, understandable code that a typical engineer can follow. Avoid single-use helpers that
  don't help readability, speculative abstractions, wrappers around simple APIs, comments that
  narrate obvious code, and defensive checks for impossible states.
- Keep the dependency footprint minimal. Check for an existing helper or a browser API first.
- Behavior changes come with tests. Visual-only work preserves API behavior, auth, validation, and
  data flow.
- Project utility scripts use Node (`.mjs` / `tsx`), not Python.

## Product direction

Inventory management is the core product. Future features (barcode lookup first, then receipt OCR,
recipes, image uploads) build on inventory and always follow this flow: detect, then editable
review, then user confirms, then create. Never silently write uncertain external data to the
database. Don't start these features unless asked.

## Troubleshooting notes

- Hydration mismatches showing injected attributes are usually browser extensions (e.g. Dark
  Reader). Rule that out before reaching for `suppressHydrationWarning`.
- If the dev server shows an obviously stale Turbopack error (e.g. `ChunkLoadError`), delete
  `.next` and restart before debugging the app.
- If production behaves differently from local, check whether the commit was pushed and deployed
  before investigating the code.
